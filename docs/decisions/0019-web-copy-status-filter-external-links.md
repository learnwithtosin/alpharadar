# 0019 — Real brand icons, plain navigation copy, status-aware list, external-link interstitial

Status: Accepted and implemented
Date: 2026-09-10
Related: docs/decisions/0014-web-visual-identity.md (the accent/chain rules this doesn't touch), docs/spec/01-PROJECT-CONSTITUTION.md §2-3 (the interstitial's source text)

## 1. Footer icons

Lucide-react ships no X (formerly Twitter) brand mark — its `X` export is the generic close/cross glyph, not a wordmark. The footer previously used plain text labels ("GITHUB"/"X") at `text-xs`, not icons at all, so there was no lucide-`X` bug in the code as such, but the underlying complaint stood regardless: too small, too dim to read as a real social link. Replaced with real icons — lucide's `Github` (a genuine, legitimate brand mark) and a hand-rolled inline SVG of the actual X logo (the well-known angular wordmark path, not the crossing-lines glyph) — both sized identically (`h-5 w-5`, 20px, up from ~12px text) with the app's existing `text-muted-foreground hover:text-foreground` interactive pattern. `aria-label`s added since the icons carry no visible text.

## 2. "Contacts" → "Opportunities"; two more reconsidered on the same grounds

Renamed everywhere a user navigates by or must understand to act: header nav link, the landing page's CTA button, the list page's heading, and the detail page's back-link — all "CONTACTS"/"Contacts" → "OPPORTUNITIES"/"Opportunities". The radar vocabulary stays as the *visual* theme (bracketed labels, the SignalDot, chain badges); it no longer appears in navigation, where "Contacts" read as a contact-us page and directly contradicted the `/opportunities` route it pointed to.

Reconsidered on the same five-second-test grounds, per the explicit invitation to drop theme jargon where a plainer word is clearer:

- **"SIGNAL STRENGTH" → "SCORE"** (detail page, above the big number). "Signal strength" evokes phone/wifi reception, not "how good is this opportunity" — the thing someone actually needs to read in five seconds.
- **"Threat" → "Risk"** (list page's column header — the only place "threat" appeared as real UI copy, not just a code comment). Unifies with the detail page's own already-plain "RISK CLASSIFICATION"/`RiskBadge` naming, which was never renamed to "threat" in the first place — this was the one place vocabulary had drifted.
- Also renamed the list's "Contact" (age) column → "Detected" and "Signal" (score) column → "Score", for the same reason and to stay internally consistent with the detail page's own "SCORE" label — not separately requested, but the same jargon-in-navigation problem in the same table.

Nothing else was touched — "LIVE," "WATCHING," "ACQUIRED," and the rest of the radar framing stand, since they weren't named and aren't navigation the five-second test governs.

## 3 & 4. Status-aware, actionability-ordered list

**What the schema can actually distinguish — checked, not assumed.** `Opportunity.status` (`OpportunityStatus`: DETECTED/VERIFYING/ACTIVE/UPCOMING/EXPIRED/REJECTED/COMPLETED) exists, but grepping the real pipeline confirms only one write path ever sets it: `opportunity-dedup.ts`'s `findOrCreateOpportunity`, once, at creation — `status: "DETECTED"`. Nothing in `verify.ts`/`score.ts`/`resolve.ts` ever transitions it afterward (the two `status: "ACTIVE"` writes in `resolve.ts` are `Project.status`, a different field entirely — read closely before assuming otherwise). `Opportunity.endsAt`/`startsAt` are equally unpopulated — `score.ts`'s own comment says so directly: "Slice 1 never sets startsAt/endsAt." So **every real opportunity today has status DETECTED and no end date**, full stop. There is no currently-populated field that distinguishes a closed mint from an open one. Inferring "closed" from age alone would have been exactly the invented rule the ask warned against, so that wasn't done.

**The filter implemented anyway, and why it's still correct to add now.** `ACTIONABLE_STATUSES = [DETECTED, VERIFYING, ACTIVE, UPCOMING]` (apps/web/app/opportunities/page.tsx) — deliberately a *different* set from `opportunity-dedup.ts`'s `OPEN_STATUSES`, which includes `REJECTED` for an unrelated reason (a later attempt should still be able to supersede a rejected one; that's a dedup-key question, not an actionability one). REJECTED is excluded here on its own terms — the pipeline decided it doesn't qualify, so it doesn't belong in "what can I act on." Against today's real data this filter is a no-op (everything is DETECTED, so everything is "live") — that's disclosed above, not hidden, and the filter starts doing real work the moment any stage actually transitions a status, without needing to be revisited.

**Reorganized around actionability, not recency.** The live bucket sorts by score descending (unscored last) rather than `detectedAt desc` — "what can I act on now," highest-signal first, matching the explicit ask ("Telegram covers reacting to new ones," this page covers browsing what's open). A closed bucket (statuses outside `ACTIONABLE_STATUSES`) renders as its own `CLOSED`-labeled section below, visually dimmed (`opacity-60`) so a closed opportunity reads as past rather than actionable, with its `Urgency` column replaced by the actual `status` value — only rendered at all when it's non-empty, so today (no closed rows exist) it doesn't appear.

## 5. External-link interstitial

New `ExternalLink` client component (`apps/web/components/external-link.tsx`) wraps any link leaving AlphaRadar for a mint page, project site, or explorer — the detail page's `OFFICIAL ACTION LINK` button and each evidence item's source URL, the only two such sites in the app (checked via `grep -rn 'target="_blank"'` across `apps/web`). One click opens a dismissible dialog (Escape, backdrop click, or CANCEL all dismiss) showing: the warning text, sourced from `01-PROJECT-CONSTITUTION.md` §2-3 (AlphaRadar never signs transactions or spends on a user's behalf; never touches seed phrases, private keys, or wallet passwords) rather than written from impression, cited inline; and the full real destination URL in monospace, so "verify the URL" is something the user can actually do right there, not just a suggestion. CONTINUE opens the real link in a new tab. **Footer socials are explicitly exempt** — GitHub and X are accounts AlphaRadar itself controls, rendered as plain `<a target="_blank">` with no wrapper, per the direct instruction not to apply this to them.

## Verification

Full suite: typecheck, lint, format, and all 344 tests pass. Live-checked via the dev server and a real browser: header/landing/list/detail nav copy all confirmed renamed; footer icons confirmed rendering as the real GitHub and X marks, properly sized; the interstitial confirmed end-to-end — clicked the real "OFFICIAL ACTION LINK" button (after temporarily setting a real `officialActionUrl` on the existing dev-test fixture, `cmttz623h0004w6h89s1aioqi` — chosen because it's already the designated safe-to-mutate row for exactly this kind of check, and reverted to `null` immediately after, confirmed via a follow-up read), watched the dialog render with the constitution-sourced text and the real URL, and confirmed CANCEL dismisses cleanly.

**What wasn't checked, disclosed rather than assumed:**

- **The populated live-table and CLOSED-section rendering** — no real opportunity currently exists to populate them with (confirmed: zero real rows in the database), and inserting fabricated non-test data into the shared dev database to force a screenshot was ruled out as inconsistent with this project's own `isTestData` discipline. Verified via TypeScript (compiles against the real Prisma-derived types) and direct code review of the filter/sort/render logic, not a live render.
- **The evidence-item source-URL interstitial specifically** — no evidence rows exist on any reachable opportunity to click through. It uses the identical `ExternalLink` component and prop pattern as the officialActionUrl site that *was* live-verified, with no additional logic specific to that call site, so this is a reasoned inference from the verified path, not an independent live check.
- **380px rendering, literally** — the available browser tool's window-resize call reports success but does not actually change the rendered viewport in this environment (confirmed again this turn: resized to 380×800, screenshot stayed ~1513px wide). Instead of skipping this, measured the header's real rendered element widths at the current viewport via `getBoundingClientRect()` (wordmark 87.16px, "OPPORTUNITIES" link 92.55px) — text widths that don't change with viewport — then hand-computed the 380px case using the actual Tailwind breakpoint values that apply below `sm:` (nav gap 16px not 24px, header-right-div gap 12px not 16px, the desktop-only scan-text span at `display:none`, only the 6px mobile dot in flow): **32px padding + 195.71px nav + 12px header gap + 46px right side ≈ 286px needed against 380px available, ~94px of slack.** A calculation from real measurements, not a screenshot, and disclosed as such.
