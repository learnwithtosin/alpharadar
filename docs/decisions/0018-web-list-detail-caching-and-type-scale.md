# 0018 — /opportunities and detail page cached; sitewide type scale raised

Status: Accepted and implemented
Date: 2026-09-10
Related: docs/decisions/0017-web-ttfb-and-spacing-scale.md (the first TTFB pass — this closes the gap it left on `/opportunities`), docs/decisions/0016-web-db-resilience.md (retry + error-boundary semantics preserved unchanged here)

## Why the previous TTFB fix left `/opportunities` untouched — and why that reasoning didn't hold

0017 deliberately left `/opportunities`' own query uncached, reasoning it was the page's "reason for existing" and had to stay live. That's the wrong bar for a database in Frankfurt against a pipeline that runs every 5 minutes: a list that's up to 60 seconds stale is not distinguishable from a live one in practice, and every request was still paying a full round trip for it. Both the list and the detail page are now cached the same way the landing page's stats already were (0017): `unstable_cache`, 60s, retry and the error boundary both preserved exactly as they were — a cache miss still runs the real, retried query, and a genuine failure (retries exhausted) still throws through to `error.tsx` uncaught, unswallowed. Caching sits in front of that path; it doesn't change what happens when the path is actually hit.

**JSON-safe DTOs, same discipline as 0017.** `unstable_cache` persists entries as JSON; Prisma's `Date` fields aren't JSON-serializable, so both cached functions return a flattened DTO (`detectedAt` as an ISO string) and the caller reconstructs a real `Date` immediately after — every downstream line (`formatAge`, `isFresh`) keeps working against the type it always has, never a string silently wearing a `Date`'s type on a cache hit. The list's DTO (`CachedOpportunityRow`) carries only what the table renders — id, project name, chain, type, score, resolved risk level, urgency, detectedAt — not the full nested Prisma shape. The detail page's DTO (`CachedOpportunityDetail`) is larger (score, evidence, risk dimensions, `scoreInputs`) but the same principle: only fields the page actually renders, typed against `@alpharadar/types`' enums rather than `string`, so `RiskTile`/`RiskBadge`/`UrgencyBadge` etc. keep their existing type safety.

**Per-item cache keys, not one shared entry.** The detail page's cached function takes `id` as an argument; Next.js incorporates the call's arguments into the cache key alongside the static key parts, so every opportunity gets its own cache entry, not one page serving every id's data.

**The supplementary Contract lookup is cached too.** A contract row is effectively immutable after ingest (verified/type/deployer are set once, at scan time) — cached the same way, still degrading to "Unknown" on failure exactly as 0016 established, unaffected by caching.

## Measured: TTFB, `next build && next start`, median of 8 requests

| Route | 0017 (uncached list/detail) | Now (cached) |
|---|---|---|
| `/` | 0.030s | 0.031s (unchanged — already cached in 0017) |
| `/opportunities` | 1.387s | **0.015s** |
| `/opportunities/[id]` | *(not measured in 0017)* | **0.020s** |

All three comfortably clear the 100ms target in steady state.

**The honest exception, with numbers.** A true cold start — the very first request for a given cache key, ever, with nothing to serve as a stale placeholder — still pays the real Frankfurt round trip: `/opportunities` measured **3.37s** cold, `/opportunities/[id]` measured **6.63s** cold (two sequential queries — opportunity, then its contract, a genuine data dependency: the contract lookup needs the opportunity's `chain`/`contractAddress` first, so it cannot run in parallel with the opportunity fetch). This is not a synchronous "every cache miss blocks" cost, though — confirmed empirically, not assumed: after the cache naturally expired past its 60s window (a real pipeline run completed in between, see below), the *first* post-expiry request to `/` served the **stale** value in 20ms while revalidating in the background, and the very next request served the fresh one — `unstable_cache` behaves as stale-while-revalidate here, not block-on-expiry. The multi-second cost is paid at most once per cache key, ever (or once per redeploy, since the cache persists in `.next/cache` across `next build`) — not once per 60-second window as the naive "TTL cache" model would suggest.

## Type scale: two tokens, `lib/typography.ts`, applied sitewide

New file, sibling to `lib/spacing.ts`, exporting `LABEL_TEXT` (`text-[13px]`, for bracketed section labels, stat-tile labels, and small field labels) and `BODY_TEXT` (`text-[15px] leading-relaxed`, for card copy, disclosures, and prose meant to be read at normal distance). Large display text (the landing hero, the detail page's score) is untouched — sized to the moment at its own call site, not tokenized, per the direct instruction that the hero itself was already right.

Applied everywhere the two roles appear:

- **`BracketHeader`** (shared — fixes every section label on every page in one place): `text-xs` (12px) → `LABEL_TEXT` (13px).
- **Landing page**: `StatTile`'s label and hint (previously `text-[0.65rem]`, 10.4px) → `LABEL_TEXT`; the "how it works" card title bumped `text-sm` → `text-base` (14px → 16px, a direct one-step heading adjustment, not a new token) and its body → `BODY_TEXT`; the pipeline-step index numeral → `LABEL_TEXT`; "what it does not do"'s boundary title → `LABEL_TEXT`, body → `BODY_TEXT`; the "Last scan..." disclosure paragraph (previously `text-xs`, 12px) → `BODY_TEXT`.
- **Detail page**: the CONTRACT panel's `Field` label (previously `text-[0.65rem]`) → `LABEL_TEXT`; `RiskTile`'s label and value spans (previously `text-xs`) → `LABEL_TEXT`; the evidence list's claim text (previously inherited `text-sm`) → `BODY_TEXT`; the evidence-type badge (previously `text-[0.65rem]`) → `LABEL_TEXT`.

**Deliberately left alone**: monospace/data text (contract addresses, deployer addresses, JSON score inputs, evidence source URLs/types) — an established density convention (docs/decisions/0015: "monospace stays scoped to literal data"), not a legibility complaint, and not something the ask named. Header/footer chrome (the scan indicator, the footer's copyright/social links) — low-emphasis navigational chrome present on every page by design, not content someone reads, left at its existing size; a judgment call, made explicitly rather than by omission.

**Responsive check — with an honest limitation.** Grepped the rendered HTML at all three routes to confirm every `sm:`/`md:`/`lg:` breakpoint-conditional class this work touches is still present and unchanged (only static font-size classes were added; no responsive grid/flex classes were edited) — `grid-cols-2 sm:grid-cols-3 lg:grid-cols-5`, `grid-cols-1 sm:grid-cols-2 md:grid-cols-5`, `lg:grid lg:grid-cols-[1.3fr_1fr]`, etc. all confirmed intact. Could not get a genuine visual check at 380px/800px, though: the available browser tool's window-resize call reports success but the rendered viewport does not actually change size in this environment (confirmed — resized to 380×800 and 800×900, screenshot dimensions stayed ~1513px wide both times). Visual verification here is real at the ~1440px-equivalent width the tool does render at; 380px/800px are unverified by screenshot, disclosed rather than silently assumed passing.
